# COMPASS Meet — 動作の仕組み

最終更新：2026-11-17（このリポジトリのコミット `0347f93` 時点）

## 1. 何をするものか

注文住宅会社（ホームランディック一級建築士事務所）の営業担当が、お客様とオンラインで打ち合わせをするためのブラウザ通話ツール。
社内で導入予定の顧客台帳「COMPASS」のカレンダーから使うことを想定しており、Google カレンダーと Google Meet の関係のように、**予定ごとに通話リンクを発行し、リンクを開くだけで参加**できる。

- 現状はお試し運用（社内テスト段階）。COMPASS 本体とはまだつながっていない（COMPASS 側の改修待ち）
- 想定人数：1 通話あたり 2〜4 人（上限 6 人）
- 録画・録音・文字起こしの機能はない

## 2. 全体の構成

```
 [参加者のブラウザ A] ──── 映像・音声（WebRTC、端末どうしで直接・暗号化） ──── [参加者のブラウザ B]
        │                                                                    │
        │ HTTPS（合図の送受信：0.6〜2.5 秒おきに取りに行く）                       │
        ▼                                                                    ▼
 ┌──────────────── Vercel（東京リージョン hnd1） ────────────────┐
 │  静的ファイル：index.html / room.html / room.js / home.js / style.css │
 │  サーバーレス関数：api/handler.js → lib/core.js                      │
 └──────────────────────────┬──────────────────────────────────┘
                            │ HTTPS（REST）
                            ▼
                 Upstash Redis（Free プラン、Vercel Marketplace 経由）
                 ＝ 合図・参加者一覧・ルーム情報の一時置き場

 STUN：stun.l.google.com:19302（各ブラウザが自分の外向きアドレスを知るため）
 TURN：なし（未設定）
```

| 部品 | 中身 | 場所 |
|---|---|---|
| 画面 | 素の HTML / CSS / JavaScript（フレームワークなし） | `meet/public/` |
| 受付（シグナリング） | Node.js 22、依存パッケージなし | `meet/lib/core.js`、入口 `meet/api/handler.js` |
| 置き場所 | Upstash Redis（REST API を fetch で直接呼ぶ） | `meet/lib/store.js` |
| 手元用サーバー | 同じ `core.js` を使う http サーバー（開発・試験用） | `meet/server.js` |
| 設定 | ルーティング・安全用ヘッダー | `meet/vercel.json`、`meet/lib/headers.json` |

- 公開先：https://compass-meet.vercel.app （Vercel プロジェクト `compass-meet`）
- ソース：GitHub `masahiro20/masa`（**公開リポジトリ**）の `meet/` フォルダ。ブランチ `claude/focused-goldberg-qo9etw` から本番に出している

## 3. 映像・音声の流れ（WebRTC）

- 参加者どうしを**全員で直接つなぐ方式（メッシュ）**。3 人なら 3 本、4 人なら 6 本の接続ができる
- 映像・音声の中身はサーバー（Vercel・Upstash）を**通らない**。WebRTC の決まりで DTLS-SRTP による暗号化が必ずかかる
- 各接続には最初から「音声 1 本・映像 1 本」の枠（トランシーバー）を作り、カメラ⇔画面共有の切り替えやカメラの入切は**枠の中身の差し替え（replaceTrack）だけ**で行う。つなぎ直し（再ネゴシエーション）は起きない
- 画面共有は `contentHint = 'detail'`、15fps（図面の細い線を優先）
- NAT 越え：STUN（Google の公開サーバー）のみ。TURN がないため、一部の社内ネットワークや携帯回線の組み合わせではつながらない可能性がある

## 4. 合図（シグナリング）の流れ

WebRTC で直接つなぐ前に、お互いの接続情報（SDP の offer / answer、ICE 候補）を交換する必要がある。これを Vercel ＋ Upstash で中継する。

Vercel の関数は「呼ばれたときだけ動き、毎回別のサーバーで動くこともある」ので、サーバーのメモリに状態を持てない。そのため：

- サーバー → ブラウザの通知は、**ブラウザが定期的に取りに行く（ポーリング）**方式
  - つなぎ始め・何か届いた直後の 15 秒：0.6 秒おき
  - 接続待ち：0.8 秒おき
  - 静かなとき：2.5 秒おき
  - 待合室：1 秒おき
- 合図は Upstash の「その人あての受け箱（リスト）」に積まれ、取りに来たときに**読むと同時に消す**（MULTI/EXEC で LRANGE と DEL を一度に）

### Redis に置くもの

| キー | 中身 | 期限 |
|---|---|---|
| `room:<ルームID>` | 件名・日時・COMPASS の予定 ID・待合室の有無・作成時刻・有効期限 | 30 日 |
| `peers:<ルームID>` | 参加者 ID → {表示名, 合言葉, 状態（waiting / joined / denied）} | 30 日（参加者は退出時・30 秒無通信で削除） |
| `seen:<ルームID>` | 参加者 ID → 最後に取りに来た時刻 | 同上 |
| `inbox:<ルームID>:<参加者ID>` | その人あての合図・チャット | 読んだら消える。最長 6 時間 |

状態（peers）と最終アクセス時刻（seen）を分けているのは、ポーリングのたびの時刻更新が「入室許可」などの状態変更を上書きしてしまう事故を防ぐため。

## 5. 一回の打ち合わせの流れ

1. **リンク発行**：担当者がトップ画面で件名・日時を入れて「リンクを作成」→ `POST /api/rooms` → ルーム ID（`abc-defg-hij` 形式）とリンクが返る。Google カレンダー追加リンク・.ics・COMPASS 予定メモ用の文を作れる
2. **入室前画面**：リンクを開くとカメラ・マイクの確認と名前入力。カメラが使えなければ音声のみ、どちらも使えなければ見る・聞くだけで参加できる
3. **参加申し込み**：`POST /api/rooms/:id/join` → 参加者 ID と合言葉（ランダム 128 ビット）が返る。以後の操作はすべてこの 2 つが必要
4. **待合室**：
   - 中に誰もいなければ、最初の人はそのまま入室
   - 誰かいれば「待機中」になり、中の全員に「○○さんが参加を求めています」が届く
   - 中の誰かが「許可」→ 入室。「断る」→ 本人に「入室できませんでした」と表示
5. **接続**：新しく入った人が、すでにいる全員に offer を送る → 相手は answer を返す → ICE 候補は 150ms ごとにまとめて送る → 映像・音声が直接つながる
6. **通話中**：マイク・カメラの入切、画面共有、チャット、参加者一覧、招待リンクのコピー。マイク・カメラの状態は合図で他の人に知らせる
7. **退出**：退出ボタンまたはページを閉じたとき `navigator.sendBeacon` で退出を通知。通知できずに回線が切れた場合も、30 秒取りに来なければ自動で外し、他の人に知らせる

## 6. API

| 呼び方 | 用途 | 認証 |
|---|---|---|
| `GET /api/config` | ブラウザが使う STUN/TURN 設定と上限人数 | なし |
| `GET /api/healthz` | 死活確認（置き場所の種類を返す） | なし |
| `POST /api/rooms` | ルーム発行（件名・開始・終了・eventRef・lobby） | なし（※） |
| `GET /api/rooms/:id` | 件名・日時・参加人数 | なし（ID を知っていれば読める） |
| `DELETE /api/rooms/:id` | ルーム削除 | 管理用 API キー（`Authorization: Bearer`） |
| `POST /api/rooms/:id/join` | 参加申し込み | なし |
| `GET /api/rooms/:id/poll?peerId=` | 自分あての合図の受け取り | 合言葉（`X-Peer-Secret` ヘッダー） |
| `POST /api/rooms/:id/{signal,chat,state,admit,deny,leave}` | 合図・チャット・状態・入室許可/拒否・退出 | 参加者 ID ＋ 合言葉（本文） |

※ `PUBLIC_CREATE=0` にすると、発行も API キー必須にできる（COMPASS とつないだ後はそうする想定）。

## 7. COMPASS とのつなぎ方（予定）

COMPASS の予定画面に「オンライン通話を追加」ボタンを付け、COMPASS のサーバーから API キー付きで `POST /api/rooms` を呼び、返ってきた URL を予定に保存して「通話に参加」ボタンとして表示する。予定を消したら `DELETE /api/rooms/:id`。
COMPASS は外部の開発元が作っているため、この改修は依頼が必要。それまでは、トップ画面で作ったリンクを COMPASS の予定メモ欄に手で貼って使う。

## 8. 試験

- `npm test`（`meet/tests/server.test.js`）：発行・待合室・許可/拒否・中継・チャット・退出・無通信の片付け・安全用ヘッダー・Upstash への命令の組み立て（10 件）
- `node tests/e2e.js`：Chromium 2 台（偽のカメラ映像）で、リンク発行 → 待合室 → 許可 → 映像・音声の双方向接続 → マイク状態 → チャット → 画面共有 → 退出までを確認。`E2E_MODE=vercel` で Vercel の入口（api/handler.js）を通した形でも確認済み
- 本番（Vercel）では、ページ表示・Upstash への接続・エラーログなしを確認。**実機のカメラでの 2 台通話は、担当者が手元で確認予定**（作業環境からは本番 URL に直接アクセスできないため）
