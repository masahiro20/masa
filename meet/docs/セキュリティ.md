## 2. 今回見つけて直した問題と、入れた対策

### 2-1. 主催者の本人確認と、権限の分離
- **「最初に来た人が主催者」を廃止。** お客様は、誰もいなくても必ず待合室で待ちます（試験で確認）。
- 主催者になれるのは次のどちらかだけです。
  1. スタッフとして本人確認でき、かつ**ルームの持ち主**（または管理者）であること
  2. **主催者用リンクの合札**（32 バイトの乱数）を持っていること。合札はアドレスの `#` 以降に入れるため、サーバーやアクセス記録には送られません。読み取ったらアドレス欄から消します。サーバー側にはハッシュだけを保存します。
- お客様用のリンクには合札が入っていないので、お客様のリンクから主催者の権限を推測・取得することはできません。
- **主催者だけができる操作**（すべてサーバー側で確認）：入室の許可・お断り、強制退出、マイクオフの依頼（個別・全員）、画面共有の停止依頼、権限の設定（お客様の画面共有・画面への書き込み・ホワイトボード・チャット・チャットの保存）、入室の締切、全員の通話の終了、文字起こしの依頼・停止。
- お客様ができること：映像・音声・チャット（許可時）・画面共有（許可時）・書き込み（許可時）・リアクション・挙手。
- スタッフの本人確認の入口は 4 つで、どれも同じ形のスタッフ情報になります（COMPASS 連携に差し替えやすい作り）。
  - **会社の Google アカウント（推奨）**：OpenID Connect の認可コード方式＋PKCE。ID トークンの署名（RS256・Google の公開鍵）、発行元、宛先、期限、nonce、メール確認済み、**会社のドメイン（hd とメールの両方）** を確かめてからログインさせます。state で CSRF を防ぎ、ログイン後の戻り先はサイト内に限ります。個人の Gmail・他社のアカウント・改ざんしたトークン・使い回しは断ります（試験 14 件）。Google 側も「内部」設定にすると二重の守りになります。
  - **社員 ID とパスワード（現在の運用）**：初期パスワードは台帳で配り、**最初のログインで本人が必ず変更**します（変更するまで打ち合わせの作成・記録の閲覧はできません）。変更後は初期パスワードと、それ以前のログイン（ほかの端末を含む）がすべて無効になります。新しいパスワードは 10 文字以上・社員 ID を含まない・単純な並びでないことを確かめ、ハッシュだけを保存します（試験 4 件）。
  - **暫定ログイン（仕組み）**：社員 ID とパスワード。パスワードは scrypt（N=16384）のハッシュで環境変数 `STAFF_ACCOUNTS` に登録します。ログインすると、署名つきの Cookie（HttpOnly・Secure・SameSite=Strict、12 時間）が発行されます。ログアウトした合札は、期限まで無効の一覧に入れます。
  - **COMPASS からの引き継ぎ（将来）**：COMPASS が発行する短命の JWT（HS256、`iss=compass`、`aud=compass-meet`、有効 10 分以内、`jti` で一度きり）を Cookie に交換します。`alg=none` や HS512 への書き換え、期限切れ、発行元違いは断ります（試験で確認）。
  - **サーバー間（将来の COMPASS 本体から）**：`MEET_API_KEY` と `X-Staff-Id` ヘッダーで、COMPASS のサーバーがスタッフに代わってルームを作れます。

### 2-2. API への不正アクセス対策
- **ルームの作成はスタッフだけ**（未ログインは 401）。
- **回数制限**を、IP だけでなく「誰が」「何に対して」で分けて数えます。

  | 対象 | 単位 | 上限 |
  |---|---|---|
  | ログインの失敗 | 回線ごと／社員 ID ごと | 20 回／15 分、5 回／15 分（成功は数えない） |
  | ルーム作成 | スタッフごと／全体 | 30 回／時、300 回／日 |
  | 入室の申し込み | 部屋ごと／部屋×回線 | 30 回／10 分、10 回／10 分 |
  | 確認コードの失敗 | 部屋ごと（回線を変えても数える） | 10 回／15 分 |
  | 取りに来（poll） | 参加者ごと | 0.35 秒より短い間隔は断る |
  | 合図・チャット・その他の操作 | 参加者ごと | 900・30・60 回／分 |
  | 主催者の操作 | 主催者ごと | 120 回／分 |
  | 参加者の操作以外の API 全般 | 回線ごと | 600 回／分 |

  参加後の操作は参加者ごとに数えるため、同じ家・会社の回線から複数のお客様が参加しても互いに止め合いません。回線（IP）は Redis にそのまま残さず、ハッシュにして数えます。
- **待合室の人数上限**（8 名）と、満員（既定 6 名）なら待合室にも入れない仕組み。
- **入力の検証**：ID は英数字と記号 64 文字以内、日時は ISO 8601（タイムゾーン付き）、終了が開始より後、開始は 180 日以内。制御文字や見えない文字（双方向制御文字を含む）は取り除きます。本文は 1MB まで、JSON 以外の送信は 415 で断ります。
- **合図の検証**：offer / answer は `v=0` で始まる 20,000 文字以内、ICE 候補は 40 件・各 800 文字以内。余分な項目は落としてから中継します。自分あての合図は断ります。
- **管理用 API**（削除・詳細）は持ち主か管理者だけ。他人の記録は 403 ではなく **404「見つかりません」** を返し、他人の記録の有無も推測させません。
- **CSRF 対策**：Cookie で認証する書き込みは、`Origin` が同じサイトであること（または `Sec-Fetch-Site: same-origin`）を必須にしています。どちらも無い送信は断ります。Cookie は SameSite=Strict、送信は JSON に限っています。
- **エラーの返し方**：内部の状態や他人の情報を含めず、決まった文言だけを返します。ログには例外のメッセージだけを出し、送られた本文・個人情報は出しません。Upstash のエラー本文もログに出しません。
- **本番で鍵が未設定なら API は止まります**（使い捨ての鍵で動かしてしまう事故を防ぐ）。

### 2-3. 通話ルームの安全管理
- 待合室 → 主催者の許可で入室（主催者がいなければ待ち続ける）。
- **全員の通話の終了**：全員に「終了しました」を知らせ、参加者の合言葉をすべて無効にします。終了の印は別のキー（`ended:<ID>`）に置き、権限の変更など他の更新で「終了」が取り消されることはありません。終了したルームには主催者も入れません（試験で確認）。
- **リンクの有効期限**：終了予定の 3 時間後まで（時刻なしは作成から 12 時間）。期限を過ぎると入室できません。
- **入室の締切（ロック）**、**強制退出**（本人に知らせ、以後の操作をすべて断り、ほかの全員は本人との直接接続を切る）。
- **リンクが転送された場合への備え**
  - 任意で **6 桁の確認コード** を付けられます（電話などで別に伝える）。失敗は部屋ごとに数えて止めます。
  - お客様の名前は自己申告ですが、主催者には**サーバーが確かめた「担当」の印**が付き、お客様が担当者になりすますことはできません。
  - 最後は主催者が待合室で確認し、知らない人は「お断り」できます。
  - お客様はアカウント登録なしのまま参加できます。

### 2-4. 顧客情報の保護
- **リンクを知っているだけでは**、件名・お客様名・顧客 ID・案件 ID・参加人数は取得できません。入室前の画面で見えるのは、日時・担当者名（社員名）・確認コードの要否だけです（試験で確認）。件名は入室を許可された人にだけ届きます。
- **待合室の人には、中にいる人の名前を見せません。**
- **保存データの暗号化**：件名・お客様名・顧客 ID・メモ・議事録・チャット・文字起こし・出入りの記録は、AES-256-GCM で暗号化してから Upstash に保存します。用途ごとに追加認証データ（例 `room:<ID>`）を付けるため、別のレコードに付け替えられても読めません。Upstash の管理画面やトークンが漏れても、中身は読めません（鍵 `DATA_KEY` は Vercel の環境変数だけにあります）。保存データに平文が残らないことを試験で確認しています。
- **参加者の合言葉は SHA-256 のハッシュだけを保存**します。比較は時間差の出ない方法で行います。
- **合言葉はアドレスに載せません**（ヘッダーで送るので、アクセス記録に残りません）。
- **保持期間**：会議記録は 180 日（`MEETING_RETENTION_DAYS`）、合図・チャットの受け箱は読んだ時点で消え、残っても最長 6 時間、参加者情報は退出か 45 秒の無通信で消えます。記録の削除は持ち主（または管理者）ができます。
- **チャットの保存**は既定でオフ。主催者がオンにしたときだけ記録に残り、画面にも「保存」と表示されます。
- **お客様向けの予定（Google カレンダー・.ics）には件名とリンクだけを入れ**、お客様名・顧客 ID は入れません。

### 2-5. 通信・データの安全性
- HTTPS（Vercel・HSTS）と、WebRTC の DTLS-SRTP による映像・音声の暗号化はそのままです。映像・音声・書き込みは端末どうしで直接やりとりし、サーバーを通りません。
- **WebRTC の接続情報**は、入室を許可された人どうしでだけ中継し、形を検証してから渡します。
- **書き込み（データチャネル）**：受け取った側で「送り主に書く権限があるか（権限はサーバーが配ったものを使い、相手の自己申告は信じない）」「消そうとしている図形が送り主のものか（主催者は全部可）」「全体の上書きは主催者からだけ」「図形の数・点の数・画像の大きさの上限」を確かめます。
- **退出・強制退出・終了した人の合言葉は無効**になり、以後の操作はできません。
- **TURN の資格情報**は、入室済みの人にだけ、有効期限つき（既定 2 時間）で発行します。誰でも見られる設定（`/api/config`）には載せません。
- **XSS 対策**：人が入力した文字はすべて `textContent` で表示します。チャットの URL は `http/https` だけをリンクにし、`rel="noopener noreferrer"` を付けます。HTML の埋め込みが無効なことをブラウザの試験で確認しています。
- **セキュリティヘッダー**：CSP（`script-src 'self'`、`frame-ancestors 'none'`、`object-src 'none'`、`base-uri 'none'` など。ページ内に直接書いたスクリプトは使っていません）、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Permissions-Policy`（カメラ・マイク・画面共有は自サイトのみ、位置情報は不可）、`X-Content-Type-Options: nosniff`。
- **依存ライブラリ**：外部の npm パッケージは使っていません（Node.js の標準機能だけ）。AI を有効にする場合だけ、Anthropic の公式 SDK を入れる想定です。PDF を読み込む場合は pdf.js（Apache-2.0）を自サーバーに置きます（未導入）。

### 2-6. 主催者の引き継ぎと、背景のぼかし（追加）

- **主催者を渡す**：主催者は参加者一覧の「主催者にする」で、ほかの参加者を主催者にできる。主催者が退出するときに、ほかに主催者がいなければ「誰に渡すか」「全員の通話を終了するか」を選ぶ画面が出る。回線が切れて抜けた場合や、何も選ばずに抜けた場合は、残っている人に自動で渡す（社員を優先し、次に早く入った人）。
- **渡された人にできないこと**：メモ・打ち合わせ記録は社員のログインで確かめるため、主催者を渡されたお客様は見られない（試験で確認）。社員として入った主催者は、ほかの人から主催者を外されたり、退出させられたりしない。
- **背景のぼかし・背景画像**：人と背景の見分け（Google MediaPipe、Apache-2.0）は、参加者の端末の中だけで行う。映像を外部に送らない。部品は本番の組み立て時に自分のサイトへ置き、外部のサイトから読み込まない。そのため CSP に `'wasm-unsafe-eval'`（WebAssembly の実行の許可。任意の文字列を実行する `unsafe-eval` とは別物）を足した。自分で選んだ背景画像は、その端末のブラウザの中にだけ保存する。

### 2-7. 録音（追加）

- 主催者は、参加者の許可なしで録音できる（社内の運用方針で決定）。ただし録音中は、参加者全員の画面に「● 録音中」と表示し、入室前の画面にも「担当者が録音する場合は表示される」と書いている。
- 録音は全員の声を 1 本にまとめ、主催者のパソコンにだけ保存する。サーバーや外部サービスには送らない。
- ブラウザが途中で落ちても失わないよう、録音中は 1 秒ごとに主催者のブラウザの中（IndexedDB）に控えを書き、次に開いたときに保存するか捨てるかを選べる。保存したら控えは消す。
- お客様は録音できない（サーバー側で主催者以外の録音の操作を断る。試験で確認）。録音の開始・停止は打ち合わせ記録に残る。

## 3. 不正な操作を模擬した試験（自動試験 47 件のうち、安全に関わるもの）

- 未ログインでのルーム作成 → 401
- 別サイトからの送信（Origin 違い・Origin なし・cross-site）、JSON 以外の送信 → 403 / 415
- パスワードの失敗の文言が、ID の有無で変わらないこと。失敗が続くと 429
- 改ざんした Cookie、ログアウト済みの Cookie → 401
- COMPASS の JWT：使い回し・期限切れ・有効時間が長すぎる・発行元違い・`alg=none` → 401
- 入室前の情報、Redis の中身に、件名・お客様名・顧客 ID・合言葉が出ないこと
- お客様による主催者の操作 9 種 → すべて 403。同時に 20 回送っても権限確認をすり抜けない
- 主催者用の合札を 2 文字変えたもの → お客様として扱う
- 持ち主でないスタッフ → 主催者になれず、記録は 404。管理者は閲覧可、ただし他人の議事録の確定は不可
- お断り・強制退出された人の合図・チャット → 403
- 他人の参加者 ID と合言葉の組み合わせ、別の部屋の合言葉、アドレスに載せた合言葉 → 403
- 終了したルームへの再入室（お客様・主催者とも）→ 410。終了後の権限変更 → 410
- 期限切れのリンク → 410
- 確認コードの総当たり → 部屋ごとに 429
- 壊れた合図・巨大な合図・自分あての合図 → 400 / 404
- 取りに来る間隔が短すぎる → 429
- 待合室の上限、満員 → 429 / 409
- 許可のない画面共有・チャット停止中のチャット → 403
- 送信者を偽ったチャットの削除 → 403
- 文字起こし：同意前・一人でも断った・途中参加者が未同意 → 記録を受け付けない
- AI 要約：承認の設定がない → 409（外部に送らない）
- 本番で鍵が未設定 → 503

ブラウザの試験（Chromium 3 台）でも、待合室・許可・強制退出・終了・再入室不可・チャットの HTML 無効化を確認しました。

## 4. 残っている課題とリスク（正直な評価）

### 重大（お客様との本番利用の前に必ず対応）
1. **本番環境は古い版のまま**です。今回の版を出すには、`DATA_KEY`・`SESSION_SECRET`・`STAFF_ACCOUNTS` の設定（＝本番の認証方式の切り替え）が必要で、ご確認が要ります。いまの本番は「最初に来た人が主催者」の旧方式です。
2. **Vercel の Hobby（無料）プランは非商用に限る規約**です。お客様との業務利用には Pro（月 20 ドル）か、別の置き場所が必要です。
3. **個人情報の取り扱いの確認**：表示名・接続情報（IP アドレスを含む）・暗号化した記録が、米国企業（Vercel・Upstash）のサービスを通ります。社内規程・プライバシーポリシーとの整合、必要ならお客様への説明を確認してください（個人情報保護法の外国にある第三者・委託の扱いは、専門家に確認を推奨）。

### 中
4. **スタッフのパスワードは暫定方式**です。多要素認証なし、パスワードの変更画面なし（環境変数で管理）、アカウントの一時停止は回数制限のみ。COMPASS のログインとの連携で置き換える前提です。
5. **主催者用リンクの合札**は、漏れるとその人が主催者になれます（有効期限はリンクと同じ）。社内の共有にとどめてください。ログインしたスタッフは合札なしで主催者になれるので、普段は合札を使わない運用を推奨します。
6. **TURN が未契約**のため、一部のネットワークではつながりません（仕組みは実装済み。契約と設定が必要）。
7. **参加者どうしに IP アドレスが見えます**（端末どうしで直接つなぐ方式の性質）。また、STUN に Google の公開サーバーを使うため、Google にも IP アドレスが届きます。TURN を入れて「中継のみ」にすれば隠せますが、通信費が増えます。
8. **画面共有の権限は、最後はお客様のブラウザが守るもの**です。サーバーは「共有中」の申告を止めますが、改造したブラウザがカメラの枠に画面を流すことまでは止められません（映像は端末どうしで直接流れるため）。書き込みの権限も、受け取る側（担当者・ほかのお客様のブラウザ）で守っています。
9. **公開リポジトリ**：ソースコードは誰でも読めます。秘密の値は含めていません。
