## 1. 見つけたセキュリティ上の問題（前回の版）
1. 最初に入室した人が主催者になる。お客様が先に入る、またはリンクが漏れると、第三者が許可役になれた
2. 入室済みの人なら誰でも、ほかの人の入室を許可できた
3. ルームの作成が、認証も回数制限もなく誰でもできた
4. 入室前の情報で、件名と予定 ID（顧客側の ID）が誰でも読めた。件名にはお客様名が入りうる
5. 待合室の人にも、中にいる人の名前の一覧を返していた（前回の説明書と食い違い）
6. 合図の中身を検証せずに保存していた（巨大なデータで容量を使い切る攻撃が可能）
7. 待合室の人数に上限がなかった
8. Redis に件名などを平文で保存していた
9. 通話を終了・ロック・強制退出する手段がなかった（リンクは 30 日間使い回せた）
10. 管理用 API キーが未設定のときは削除が誰でもできた（前回の手直しで修正済み）

## 2. 直したセキュリティ対策　【完了・試験済】
詳しくは「セキュリティ.md」に書いています。
- 主催者の本人確認（暫定ログイン／COMPASS の JWT 引き継ぎ口／サーバー間 API キー）と、主催者・参加者の権限の分離
- お客様は必ず待合室で待ち、主催者だけが許可できる
- 強制退出、マイクオフの依頼、画面共有の停止依頼、権限の設定、入室の締切、全員の通話の終了（再利用不可）、有効期限、確認コード
- 回数制限（ログインの失敗、作成、入室、確認コード、取りに来る間隔、合図、チャット、主催者の操作、API 全般）。正規のお客様が同じ回線にいても止め合わない数え方にした
- 入力・合図の形式の検証、CSRF 対策、JSON 以外の送信を拒否、決まった文言だけのエラー、ログに個人情報を出さない
- 件名・お客様名・メモ・議事録・チャット・文字起こし・出入りの記録を AES-256-GCM で暗号化して保存。合言葉はハッシュだけを保存。合言葉はアドレスに載せない
- リンクを知っているだけでは、件名・お客様名・顧客 ID・参加人数は取得できない
- 書き込み（データチャネル）は、受け取る側で権限と図形の持ち主を確かめる
- TURN の資格情報は、入室済みの人にだけ期限つきで発行
- CSP、X-Frame-Options、Referrer-Policy、Permissions-Policy などのセキュリティヘッダー
- 本番で鍵が未設定なら API を止める

## 12. COMPASS との連携に必要なこと
COMPASS の開発元にお願いすることは次のとおりです。
1. **ログインの引き継ぎ**：COMPASS にログインしているスタッフが「オンライン商談を開く」を押したら、COMPASS のサーバーが短命の JWT を作り、COMPASS Meet の `/api/auth/compass` に渡します。JWT の内容は HS256、`iss=compass`、`aud=compass-meet`、`sub=社員ID`、`name`、`iat`、`exp`（10 分以内）、`jti`（一度きり）です。共有の鍵（`COMPASS_JWT_SECRET`）を両方に設定します。
2. **予定からの作成**：COMPASS のサーバーから `POST /api/rooms` を呼び、件名・お客様名・顧客 ID・案件 ID・予定 ID・日時を渡します。認証は `MEET_API_KEY` と `X-Staff-Id`。返ってきたお客様用リンクを予定に保存し、お客様へのメッセージに差し込みます。
3. **予定の取り消し**：予定を消したら `DELETE /api/rooms/:id`。
4. **記録の取り込み**：打ち合わせ後に記録（メモ・決定事項・宿題・確定した議事録）を COMPASS の顧客情報に取り込む API（Meet 側に、サーバー間の読み取り口を追加する必要あり）。
5. **社員の名簿**：COMPASS の社員 ID を正とし、暫定の `STAFF_ACCOUNTS` は廃止します。
