AI駆動開発と仕様駆動開発の違いは、**AI駆動開発が「AIを中心に開発を進める」という広い考え方であるのに対し、仕様駆動開発は「仕様を開発の中心に置き、その仕様からAIに計画・タスク・実装を進めさせる」具体的な進め方**だという点です。つまり、両者は対立するものではなく、**仕様駆動開発はAI駆動開発を進めるための方法の一つ**と考えると分かりやすいでしょう。

GitHubは2025年9月に、仕様駆動開発のためのオープンソースのツールキット「Spec Kit」を公開しました。同社のブログでは、仕様を一度書いて終わりにせず、仕様が実装やタスクの分解を導く「生きた成果物」として扱う考え方が紹介されています。

## AI駆動開発と仕様駆動開発の違いを比較

まずは両者の違いを一覧で整理します。どちらも使われ方に幅がある言葉なので、一般的な捉え方として見てください。

| 観点 | AI駆動開発 | 仕様駆動開発 |
| --- | --- | --- |
| 言葉の範囲 | AIを中心にした開発の進め方全般 | 仕様を中心に置く、具体的な開発の進め方 |
| 中心になるもの | AIへの指示、検証、計画など | 仕様（何を・なぜ作るか）と、そこから導く計画・タスク |
| 進め方 | チームや目的に応じてさまざま | 仕様→計画→タスク→実装の順に段階を踏む |
| 人の主な役割 | 目的を伝え、任せ、確かめる | 仕様と計画を舵取りし、各段階を確認する |

**AI駆動開発という大きな枠の中に、仕様駆動開発という一つの型がある**、という関係です。

## 仕様駆動開発が生まれた背景

GitHubのブログでは、コーディングエージェントが強力になる中で、「目的を説明するとコードが返ってきて、正しそうに見えるが、うまく動かない」というパターンが生まれていると指摘されています。こうした「バイブコーディング」的な進め方は、素早い試作には向いているものの、本格的なアプリケーションの開発や既存のコードベースでの作業では信頼性が下がると説明されています。

同ブログは、問題はコーディングエージェントの能力ではなく進め方にあるとし、**仕様を静的な文書ではなく、プロジェクトとともに進化する「生きた、実行可能な成果物」として扱う**ことを提案しています。仕様がチーム共通の「信頼できる情報源」になり、分からないことがあれば仕様に立ち返り、プロジェクトが複雑になれば仕様を洗練させる、という考え方です。

バイブコーディングとの違いは {{link:ai-kudou-kaihatsu-vibe-coding-chigai|AI駆動開発とバイブコーディングの違い}} でも詳しく整理しています。

## 仕様駆動開発の4つの工程

GitHubのブログによると、Spec Kitを使った仕様駆動開発は、明確なチェックポイントを持つ4つの工程で進みます。**各工程にはそれぞれの役割があり、現在の段階が十分に確認できるまで次に進まない**のが重要なポイントとされています。

:::steps 仕様駆動開発の4ステップ
1. **Specify（仕様）**：何を作るのか、なぜ作るのかを高いレベルで説明し、コーディングエージェントが詳細な仕様を作成します。技術や設計ではなく、利用者の体験や「成功とは何か」に焦点を当てます。
2. **Plan（計画）**：使いたい技術、アーキテクチャ、制約などを伝え、コーディングエージェントが技術的な実装計画を作成します。社内の標準技術や、既存システムとの連携、性能の目標などもここで伝えます。
3. **Tasks（タスク）**：仕様と計画をもとに、コーディングエージェントが作業を小さく、レビューしやすい単位に分解します。各タスクは単独で実装・テストできるものにします。
4. **Implement（実装）**：コーディングエージェントがタスクを一つずつ（可能なものは並行して）実装し、開発者は特定の問題を解決する、焦点の絞られた変更をレビューします。
:::

同ブログでは、タスクを「認証を作る」ではなく「メールアドレスの形式を検証するユーザー登録の仕組みを作る」のように具体的にすることで、エージェントが自分の作業を検証しやすくなると説明されています。また、**人の主な役割は舵取りで、文章の大部分はコーディングエージェントが書く**とされています。

## 仕様（Specify）の段階で書く内容の例

最初の「仕様」の段階では、技術の話よりも「誰のために、何を、なぜ作るのか」を言葉にすることが大切です。GitHubのブログでも、この段階は技術スタックやアプリの設計ではなく、利用者の行動や体験、成功の姿についてのものだと説明されています。たとえば次のような問いに答える形で整理すると、仕様を書きやすくなります。

- この機能を使うのは誰か
- その人のどんな困りごとを解決するのか
- 利用者は、どのような流れで機能を使うのか
- どのような結果になれば「成功」と言えるのか

**ここで目的と成功の条件を具体的にしておくほど、計画やタスクの段階でAIの出力が意図からずれにくくなります**。技術的な制約や使いたいツールは、次の計画の段階でまとめて伝えるようにしましょう。

## 仕様駆動開発とClaude Codeのベストプラクティスの共通点

仕様駆動開発の考え方は、AIコーディングツールの公式ドキュメントで勧められている進め方とも重なります。たとえばClaude Codeの公式ベストプラクティスでは、いきなりコーディングさせると間違った問題を解くコードが生まれる可能性があるとして、探索・計画・実装・コミットの流れで進めることが紹介されています。また、テストやビルドなど、AIが自分の作業を検証できる方法を渡すことが最初に挙げられています。

**「まず何を作るかを明確にし、計画を確認し、検証できる単位で進める」**という点で、仕様駆動開発とAIコーディングの基本的な進め方は共通しています。

## 仕様駆動開発のメリットと注意点

:::merit 仕様駆動開発のメリット
- 何を・なぜ作るのかが明確になり、AIの出力が意図からずれにくい
- 作業が小さなタスクに分かれるため、レビューしやすい
- 仕様がチーム共通の情報源になり、認識のずれを減らせる
:::

:::demerit 仕様駆動開発の注意点
- 仕様や計画を作る工程に時間がかかる
- 小さな修正や試作には、手順が重く感じられることがある
- 仕様を更新し続けないと、実装と仕様がずれていく
:::

:::warning すべての作業に使う必要はない
Claude Codeの公式ベストプラクティスでも、差分を1文で説明できる程度の小さな変更なら、計画を省略してよいとされています。仕様駆動開発は、新しい機能の開発や複雑な変更など、手順を踏む価値がある場面で取り入れるのが現実的です。
:::

## どんな場面で仕様駆動開発を取り入れるべきか

| 場面 | おすすめの進め方 |
| --- | --- |
| 個人の試作、アイデアの検証 | 手軽に試し、動くものを早く作る |
| 小さなバグ修正や文言の変更 | 直接依頼し、変更を確認する |
| 新しい機能の開発 | 仕様と計画を作ってから実装する |
| 既存の大きなコードベースでの変更 | 仕様・計画・タスクに分け、各段階を確認する |
| チームでの開発 | 仕様を共通の情報源として共有する |

GitHubのブログでは、Spec KitがGitHub Copilot、Claude Code、Gemini CLIなどのコーディングエージェントと組み合わせて使えると紹介されています。ツールの料金を確認したい人は {{link:claude-code-ryokin|Claude Codeの料金}}、AI駆動開発の学び方全体は {{link:ai-kudou-kaihatsu-manabikata-engineer|AI駆動開発の学び方}} を参考にしてください。

## 仕様駆動開発を学ぶときのポイント

:::check 取り入れる前に確認したいこと
- 作りたいものの目的と、成功の条件を文章で説明できるか
- 使う技術や制約を、計画の段階で伝えられるように整理したか
- タスクごとに、動作を確かめるテストや確認方法を用意できるか
- 仕様を更新し続ける運用を、チームで決めているか
:::

**仕様駆動開発の核心は、ツールそのものよりも「何を作るかを言葉にし、段階ごとに確かめる」習慣**にあります。まずは小さな機能で、仕様→計画→タスク→実装の流れを試してみましょう。

AIコーディングツールを使った実践的な進め方を短期間で身につけたい人は、{{aff:learning-ai-coding|Claude Codeを実践的に学べる研修}}で、仕様や計画を活かした使い方を学ぶのも一つの方法です。

## よくある質問

### 仕様駆動開発とは？

仕様を開発の中心に置き、その仕様から計画・タスク・実装を進める開発の進め方です。GitHubのブログでは、仕様を一度書いて終わりにせず、プロジェクトとともに進化する「生きた成果物」として扱う考え方が紹介されています。

### AI駆動開発と仕様駆動開発はどちらを学ぶべき？

両者は対立するものではなく、仕様駆動開発はAI駆動開発を進める方法の一つです。まずはAIコーディングの基本を押さえ、新しい機能の開発など手順を踏む価値がある場面で、仕様駆動開発を取り入れていくのがおすすめです。

### Spec Kitとは？

GitHubが公開した、仕様駆動開発のためのオープンソースのツールキットです。Specify・Plan・Tasks・Implementの4つの工程で、コーディングエージェントと一緒に開発を進める仕組みが用意されています。

### 仕様駆動開発はClaude Codeでも使える？

GitHubのブログでは、Spec KitがClaude Codeを含む複数のコーディングエージェントと組み合わせて使えると紹介されています。また、Claude Code自体の公式ドキュメントでも、計画してから実装する進め方が勧められています。
